## 工作原理

### 推测式扇出

这里演示的核心模式是[推测式扇出](https://docs.typesafe.ai/patterns/fan-out)。每个用户请求都会对着一长串问题被评估，其中很多问题对大多数请求来说最终都用不上。

先看下面这个用户请求：

> 用户请求原文：「Turn off all of the lights in the house」（把房子里所有的灯都关掉）

这是一个非常简单的请求，我们的代码只需要关心以下几个问题的答案：

- 「这个请求属于哪一类？」（smarthome command）
- 「这个请求针对哪个域？」（whole house）
- 「这个请求针对哪种设备？」（lights）
- 「应该对这些灯执行什么动作？」（turn off）

注意最后一个问题是这样写的：它假设用户正在对灯下达命令 —— 而我们是在还不知道用户实际在请求什么之前就把它问出去的。这就是我们所说的「推测性问题（speculative question）」：在还不知道它是否相关之前就先问，这样所有问题就能并行评估，之后再靠代码把不相关的结果过滤掉。这是构建系统的关键模式，让同一套问题就能应付各式各样的用户请求。

#### 错误做法：串行 API 调用

错误做法是：把这些问题拆成多次 API 调用，等你确定需要某个答案时再去问它：

- 「这个请求属于哪一类？」（smarthome command）

然后，只有在你确定它是智能家居命令之后：

- 「这个请求针对哪个域？」（whole house）
- 「这个请求针对哪种设备？」（lights）

再然后，只有在你确定它针对的是灯之后：

- 「应该对这些灯执行什么动作？」（turn off）

这种做法追求的是问题数量最少，但最终会比把全部问题一次性打包成一次 API 调用要慢得多、也贵得多。

### TypeSafe 与 LLM 的搭配

这个演示还展示了 TypeSafe 如何与 LLM 配合，来处理有时需要一步文本生成的系统：

**拆分复合的用户请求：** 这个演示里有一个 Noul 问题，用来判断用户的请求是否要求不止一个不同的动作。如果为真，系统就用一个 LLM 把这个请求拆成一串原子命令。拆分出来的请求再逐个交给 TypeSafe 评估。

**回退到对话式 LLM：** 当 TypeSafe 判定用户的查询是在索要一般信息或是在闲聊时，系统就调用一个 LLM 来生成一段自由形式的回答。这让一个交互式系统能以快而省的方式处理那些行为已知、确定可预测的请求，同时在需要时仍保留生成式 LLM 带来的灵活性。相比 LLM 的响应，TypeSafe 的首次响应快得多，所以它给整个系统带来的延迟几乎可以忽略。
